# รายงานจุดเสี่ยง — ตรวจกับระบบ production จริง

> วิธีตรวจ: ยิงคำขอจริงเข้าระบบที่ใช้งานอยู่ด้วยสิทธิ์ของคนนอก (anon key)
> ไม่ใช่การอ่านโค้ดแล้วสรุปเอา ผลด้านล่างคือสิ่งที่เกิดขึ้นจริง

---

## 🔴 วิกฤต — พบและแก้แล้ว

### R-01 · ผู้ใช้มือถือส่งแจ้งซ่อมไม่ได้เลย

| | |
|---|---|
| **อาการ** | อัปโหลดรูปจากกล้องมือถือ → ขึ้นหน้า "เกิดข้อผิดพลาดชั่วคราว" ทุกครั้ง |
| **สาเหตุ** | Server Actions ของ Next.js จำกัด request body ไว้ **1MB** โดยดีฟอลต์ แต่รูปจากกล้องมือถือปกติ **2-6MB** |
| **ความร้ายแรง** | ระบบใช้งานไม่ได้จริงกับกลุ่มเป้าหมายหลัก ทั้งที่หน้าเว็บดูปกติดีทุกอย่าง |
| **พิสูจน์** | ส่งรูป 5.65MB เข้า production → ล้มเหลว |
| **แก้แล้ว** | ย่อรูปในเครื่องผู้ใช้ก่อนส่ง (ด้านยาวสุด 1600px, JPEG q0.82) + ตั้ง `bodySizeLimit: 4mb` เป็นตาข่ายรอง |
| **ยืนยันหลังแก้** | รูปเดิม 5.65MB → เหลือ 942KB → ส่งผ่าน ได้รหัสติดตาม |

> น่าจะตรงกับที่ลูกค้าแจ้งว่า "พอไม่ได้ใช้บราวเซอร์มันหลุดออกเอง" — ควรถามยืนยัน
> ผลพลอยได้: อัปโหลดเร็วขึ้นมากบนเน็ตมือถือ ประหยัดพื้นที่เก็บ และลดค่า AI เพราะภาพเล็กลง

## 🟡 ต้องจัดการก่อนเปิดใช้จริงวงกว้าง

### R-02 · ไม่มีการจำกัดจำนวนการแจ้งซ่อมต่อคน (ไม่มี rate limit)

ฟอร์มเปิดสาธารณะและไม่ต้องล็อกอิน ใครก็ยิงซ้ำได้ไม่จำกัด แต่ละใบใช้ทรัพยากรจริง:
พื้นที่เก็บรูป + **เรียก AI ซึ่งมีค่าใช้จ่ายต่อครั้ง**

- **ตอนนี้ยังไม่เสียเงิน** เพราะยังไม่ได้ตั้ง `ANTHROPIC_API_KEY`
- **แต่วินาทีที่ใส่คีย์ ความเสี่ยงนี้กลายเป็นค่าใช้จ่ายทันที**

**แนะนำก่อนใส่คีย์ AI:** จำกัดจำนวนใบต่อ IP ต่อชั่วโมง + ตั้งเพดานยอดใช้จ่ายรายเดือนที่ฝั่งผู้ให้บริการ AI

### R-03 · ยังไม่มีนโยบายลบข้อมูลส่วนบุคคล (PDPA)

ระบบเก็บ **เบอร์โทร ชื่อผู้แจ้ง และรูปถ่าย** ซึ่งเป็นข้อมูลส่วนบุคคล แต่ยังไม่มีรอบลบอัตโนมัติ
เก็บสะสมไปเรื่อย ๆ ไม่มีกำหนด

**แนะนำ:** กำหนดระยะเก็บ (เช่น 1 ปีหลังปิดงาน) แล้วตั้งงานลบตามรอบ

### R-04 · เจ้าหน้าที่ทุกคนมีสิทธิ์เท่ากัน

ใครที่อยู่ในตาราง `staff` ทำได้ทุกอย่างเหมือนกันหมด ไม่มีระดับผู้ดูแล
ยังไม่เป็นปัญหาตอนมีเจ้าหน้าที่น้อยราย แต่ควรวางแผนไว้

## 🟢 ตรวจแล้วปลอดภัย

### ความลับและข้อมูลส่วนบุคคลใน repo สาธารณะ

| ตรวจ | ผล |
|---|---|
| ไฟล์ `.env*` ถูก commit ไหม | ไม่มี — `.gitignore` ครอบ `.env*` และ `.vercel` |
| คีย์ลับใน git history | ไม่พบ (เจอแค่ชื่อตัวแปรในเอกสาร) |
| อีเมล/เบอร์โทร/ชื่อบุคคล/รหัสนักศึกษา | ไม่พบเลย |

### สิทธิ์การอ่านข้อมูล (ยิงจริงด้วย anon key)

| ทดสอบ | ผล |
|---|---|
| อ่านตาราง `reports` (ชื่อ/เบอร์ผู้แจ้ง) | คืนค่าว่าง — ปิด |
| อ่านตาราง `staff` | คืนค่าว่าง — ปิด |
| อ่าน `report_status_history` | คืนค่าว่าง — ปิด |
| อ่าน `buildings` | เปิด (ตั้งใจ — ต้องใช้ทำ dropdown) |

### สิทธิ์การเขียนและการยกระดับสิทธิ์

| ทดสอบ | ผล |
|---|---|
| แทรกใบพร้อมตั้ง `status='done'` เอง | **401 ปฏิเสธ** — RLS บล็อก |
| แก้สถานะใบที่มีอยู่ (PATCH) | กระทบ **0 แถว** — ใบยังเป็น `pending` เหมือนเดิม |
| ลบใบ (DELETE) | กระทบ 0 แถว — ใบยังอยู่ |

> ข้อควรรู้: PostgREST คืน `204` ทั้งกรณีสำเร็จและกรณีไม่เจอแถว
> จึงต้องยืนยันด้วยการอ่านสถานะจริงซ้ำ ไม่ใช่ดูแค่รหัสตอบกลับ

### รูปถ่ายใน Storage

| ทดสอบ | ผล |
|---|---|
| เปิดรูปผ่าน public URL | `Bucket not found` — บัคเก็ตเป็นส่วนตัวจริง |
| เปิดรูปด้วย anon key | `Object not found` — ปิด |
| ขอรายชื่อไฟล์ในบัคเก็ต | คืนค่าว่าง — ปิด |
| ขอสร้าง signed URL เอง | ปฏิเสธ — ปิด |

บัคเก็ตยังตั้งเพดานไฟล์ 10MB และรับเฉพาะ JPEG/PNG/WEBP

## สรุปสำหรับตัดสินใจ

**ระบบปลอดภัยตามที่ออกแบบไว้** — คนนอกแจ้งซ่อมได้อย่างเดียวจริง ๆ อ่าน แก้ ลบ หรือดูรูปของคนอื่นไม่ได้เลย
ทั้งหมดบังคับที่ชั้นฐานข้อมูล ไม่ใช่แค่ซ่อนปุ่ม

**สิ่งที่ต้องทำก่อนเปิดใช้วงกว้าง** เรียงตามลำดับ:

1. ใส่ `ANTHROPIC_API_KEY` **พร้อมกับ** ตั้ง rate limit และเพดานค่าใช้จ่าย (R-02)
2. กำหนดนโยบายระยะเก็บข้อมูลส่วนบุคคล (R-03)
3. ถามลูกค้ายืนยันว่าอาการ "หลุดออกเอง" ตรงกับ R-01 ที่แก้ไปแล้วหรือไม่
