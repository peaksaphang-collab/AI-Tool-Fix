# ระบบแจ้งซ่อม (Repair Notify System) — คู่มืออธิบายระบบ

เว็บใช้งานจริง: **https://ai-tool-fix.vercel.app**

เอกสารนี้อธิบายว่าระบบทำงานอย่างไร ใช้เทคโนโลยีอะไร และเจ้าหน้าที่ใช้งานยังไง
เขียนให้คนที่ไม่ใช่โปรแกรมเมอร์อ่านเข้าใจได้

---

## 1. ระบบนี้ทำอะไร

แทนที่การแจ้งซ่อมด้วยกระดาษ/โทรศัพท์ ด้วยเว็บที่ **ถ่ายรูปแล้วส่งได้เลย**
โดยมี AI ช่วยวิเคราะห์รูปให้อัตโนมัติว่าอุปกรณ์อะไรเสีย ประเภทงานซ่อมไหน และด่วนแค่ไหน

แบ่งเป็น 2 ฝั่ง:

| ฝั่ง | ใครใช้ | ต้องล็อกอินไหม |
|---|---|---|
| **หน้าแจ้งซ่อม** (`/report`) | ใครก็ได้ — นักศึกษา อาจารย์ เจ้าหน้าที่ | ไม่ต้อง |
| **แดชบอร์ด** (`/dashboard`) | เจ้าหน้าที่ซ่อมบำรุงเท่านั้น | ต้องล็อกอิน |

---

## 2. Flow การทำงาน (ตั้งแต่แจ้งจนปิดงาน)

```
ผู้แจ้ง                     ระบบ                        เจ้าหน้าที่
  │                          │                              │
  │ 1. เปิดเว็บ /report      │                              │
  │ 2. ถ่ายรูปสิ่งที่เสีย     │                              │
  │ 3. เลือกอาคาร → ห้อง     │                              │
  │    (ประเภทงาน/ชื่อ/เบอร์  │                              │
  │     ไม่บังคับ)           │                              │
  │ 4. กด "แจ้งซ่อม" ───────►│                              │
  │                          │ 5. อัปโหลดรูปเข้าที่เก็บ      │
  │                          │    แบบปิด (private bucket)   │
  │                          │ 6. ส่งรูปให้ AI วิเคราะห์:    │
  │                          │    - อุปกรณ์อะไร             │
  │                          │    - เสียยังไง               │
  │                          │    - ประเภทงานซ่อม (1-5)     │
  │                          │    - ความด่วน (วิกฤต/ด่วน/   │
  │                          │      ปานกลาง/ไม่เร่งด่วน)     │
  │                          │ 7. บันทึกใบแจ้ง สถานะ        │
  │                          │    "รอดำเนินการ" ──────────► │ 8. เด้งแจ้งเตือน
  │ ◄── "แจ้งซ่อมเรียบร้อย"  │                              │    ทันที (realtime)
  │                          │                              │
  │                          │ ◄────────────────────────────│ 9. กด "เริ่มซ่อม"
  │                          │        สถานะ = กำลังซ่อม      │
  │                          │ ◄────────────────────────────│ 10. กด "ซ่อมเสร็จแล้ว"
  │                          │        สถานะ = เสร็จแล้ว      │     หรือ "ดำเนินการไม่ได้"
  │                          │ 11. บันทึกประวัติทุกครั้งที่    │
  │                          │     เปลี่ยนสถานะ (timeline)   │
```

**จุดสำคัญ:** ถ้า AI วิเคราะห์ไม่ได้ (เช่นไม่ได้ตั้ง API key) ระบบ**ยังรับแจ้งซ่อมได้ปกติ**
แค่ช่องวิเคราะห์จะว่างไว้ให้เจ้าหน้าที่กรอกเอง — ไม่มีทางที่ใบแจ้งจะหาย

## 3. ใช้โปรแกรม / เทคโนโลยีอะไรบ้าง

| ส่วน | ใช้อะไร | ทำหน้าที่อะไร |
|---|---|---|
| หน้าเว็บ | **Next.js 16** (React + TypeScript) | ทั้งหน้าบ้านและหลังบ้านอยู่ในตัวเดียว |
| หน้าตา/ดีไซน์ | **Tailwind CSS + shadcn/ui** | ธีมฟ้า-ขาว, รองรับมือถือ-แท็บเล็ต-คอม |
| ฟอนต์ | **IBM Plex Sans Thai** | ฟอนต์ไทยอ่านง่าย มีน้ำหนักครบ |
| ฐานข้อมูล | **Supabase (PostgreSQL)** | เก็บใบแจ้งซ่อม อาคาร ห้อง ผู้ใช้ ประวัติ |
| เก็บรูป | **Supabase Storage** (bucket แบบปิด) | รูปไม่เปิดสาธารณะ ดูได้เฉพาะเจ้าหน้าที่ |
| ล็อกอิน | **Supabase Auth** | อีเมล + รหัสผ่าน |
| เรียลไทม์ | **Supabase Realtime** | ใบแจ้งใหม่เด้งขึ้นแดชบอร์ดทันทีไม่ต้องรีเฟรช |
| AI วิเคราะห์รูป | **Claude (Anthropic) Vision** | ดูรูปแล้วบอกว่าอะไรเสีย ด่วนแค่ไหน |
| โฮสต์เว็บ | **Vercel** | push โค้ดขึ้น GitHub แล้ว deploy อัตโนมัติ |
| เก็บโค้ด | **GitHub** | `peaksaphang-collab/AI-Tool-Fix` |

> **ตอบคำถามที่ถามมา:** ระบบนี้ **ไม่ได้ใช้ SQLite** ครับ
> ใช้ **PostgreSQL** ผ่าน Supabase ซึ่งเป็นฐานข้อมูลบนคลาวด์
> เหตุผล: SQLite เป็นไฟล์เดียวบนเครื่อง เหมาะกับแอปเครื่องเดียว
> แต่ระบบนี้ต้องให้หลายคนแจ้งพร้อมกันจากหลายที่ และเจ้าหน้าที่เห็นเรียลไทม์
> จึงต้องใช้ฐานข้อมูลบนเซิร์ฟเวอร์ที่รองรับหลายคนพร้อมกัน

## 4. โครงสร้างข้อมูล (ตารางในฐานข้อมูล)

| ตาราง | เก็บอะไร |
|---|---|
| `buildings` | รายชื่ออาคาร |
| `rooms` | ห้องในแต่ละอาคาร (ผูกกับอาคาร) |
| `service_types` | ประเภทงานซ่อม 5 อย่าง (ยกมาจากระบบเดิม ให้เลข 1-5 ตรงกัน) |
| `staff` | บัญชีเจ้าหน้าที่ (ผูกกับระบบล็อกอิน) |
| `reports` | ใบแจ้งซ่อม — รูป, อาคาร, ห้อง, ผู้แจ้ง, เบอร์, ผล AI, สถานะ, ผู้รับผิดชอบ |
| `report_status_history` | ประวัติการเปลี่ยนสถานะทุกครั้ง (ใช้ทำ timeline) |

**สถานะของใบแจ้ง:** `รอดำเนินการ` → `กำลังซ่อม` → `เสร็จแล้ว`
(หรือปิดเป็น `ดำเนินการไม่ได้` ซึ่งไม่นับเป็นงานที่ซ่อมสำเร็จ และเปิดกลับมาใหม่ได้)

## 5. ความปลอดภัย

ระบบใช้ **Row Level Security (RLS)** ของ PostgreSQL คือกำหนดสิทธิ์ที่ตัวฐานข้อมูลเลย
ไม่ใช่แค่ซ่อนปุ่มบนหน้าเว็บ — ต่อให้ยิงคำสั่งตรงเข้าฐานข้อมูลก็ทำไม่ได้

| ใคร | ทำอะไรได้ |
|---|---|
| คนทั่วไป (ไม่ล็อกอิน) | อ่านรายชื่ออาคาร/ห้อง/ประเภทงาน · ส่งใบแจ้งใหม่ · อัปโหลดรูป (เฉพาะ JPEG/PNG/WEBP ไม่เกิน 10 MB) |
| คนทั่วไป | **อ่านใบแจ้งไม่ได้ · ดูรูปไม่ได้ · แก้สถานะไม่ได้ · ดูชื่อ-เบอร์ผู้แจ้งไม่ได้** |
| เจ้าหน้าที่ (ล็อกอิน) | เห็นทุกใบแจ้ง · ดูรูป · เปลี่ยนสถานะ · มอบหมายงาน |

**ผลทดสอบเจาะระบบจริง (10 ส.ค. 2569):**

- อัปโหลดไฟล์ `.txt` เข้าที่เก็บรูป → ถูกปฏิเสธ (415)
- ยิงใบแจ้งที่ตั้งสถานะ "เสร็จแล้ว" เอง → ถูกปฏิเสธ (401)
- อ่านชื่อ/เบอร์ผู้แจ้งโดยไม่ล็อกอิน → ได้ผลลัพธ์ว่างเปล่า
- ฟอร์มแจ้งซ่อมปกติ → ยังทำงานได้ (201) ✅

## 6. คู่มือเจ้าหน้าที่ (Admin)

### เข้าระบบ
1. เปิด https://ai-tool-fix.vercel.app
2. กด **"เข้าสู่ระบบเจ้าหน้าที่"**
3. ใส่อีเมล + รหัสผ่านที่ได้รับ

### หน้าแดชบอร์ด (`รายการแจ้งซ่อม`)
- แบ่ง 2 ฝั่ง: **ยังไม่เสร็จ** / **จบงานแล้ว**
- เรียงตามความด่วนก่อน แล้วค่อยเรียงตามเวลาล่าสุด
- ใบที่ค้างเกิน 24 ชั่วโมง จะขึ้นป้าย **"ค้างนาน"** สีแดง
- **ช่องค้นหา** ด้านบน: พิมพ์ชื่ออาคาร ห้อง อุปกรณ์ ชื่อผู้แจ้ง หรือเบอร์โทรได้
- **กดที่รูป** เพื่อดูขนาดเต็ม
- **กดที่เบอร์โทร** เพื่อโทรออกได้เลย (บนมือถือ)
- ปุ่มจัดการ: `เริ่มซ่อม` · `ซ่อมเสร็จแล้ว` · `ดำเนินการไม่ได้` (มีหน้าต่างยืนยัน)
- ช่อง **ผู้รับผิดชอบ** เลือกมอบหมายงานให้เจ้าหน้าที่คนใดคนหนึ่งได้

### หน้าสรุปข้อมูล (`สรุปข้อมูล`)
ดูภาพรวม: จำนวนงานแต่ละสถานะ, กระดาน Kanban, ไทม์ไลน์, ปฏิทิน, แผนที่ความหนาแน่น (heatmap), แยกตามอาคาร/ประเภทงาน

### เพิ่มบัญชีเจ้าหน้าที่ใหม่
1. เข้า Supabase → **Authentication → Users → Add user → Create new user**
2. ใส่อีเมล + รหัสผ่าน ติ๊ก *Auto Confirm User*
3. เข้า **SQL Editor** รันคำสั่งนี้ (แก้ UID กับชื่อให้ตรง):

```sql
insert into staff (id, full_name)
values ('<UID-ที่คัดลอกมา>', 'ชื่อเจ้าหน้าที่')
on conflict (id) do update set full_name = excluded.full_name;
```

### เพิ่มอาคาร / ห้อง
เข้า Supabase → **Table Editor** → ตาราง `buildings` หรือ `rooms` → กด Insert row

## 7. การดูแลระบบต่อ

- **แก้โค้ดแล้วขึ้นเว็บ:** push ขึ้น branch `main` บน GitHub → Vercel deploy ให้อัตโนมัติ ไม่ต้องกดอะไร
- **ค่าตั้งค่าที่จำเป็น (Environment Variables บน Vercel):**
  - `NEXT_PUBLIC_SUPABASE_URL`
  - `NEXT_PUBLIC_SUPABASE_ANON_KEY`
  - `ANTHROPIC_API_KEY` *(ไม่ใส่ก็ใช้งานได้ แต่ AI จะไม่วิเคราะห์รูปให้)*
- **ไฟล์ migration ฐานข้อมูล:** อยู่ใน `supabase/migrations/` เรียงตามลำดับ 0001 → 0007

## 8. ระบบติดตามสถานะสำหรับผู้แจ้ง (เพิ่มใหม่)

### ผู้แจ้งใช้ยังไง
1. แจ้งซ่อมเสร็จ ระบบให้ **รหัสติดตาม 6 ตัว** เช่น `RP8F3K` (มีปุ่มคัดลอก)
2. เข้าหน้า **ติดตามสถานะ** (`/track`) จากหน้าแรก
3. กรอกรหัส → เห็นแถบความคืบหน้า **รับเรื่องแล้ว → กำลังซ่อม → ซ่อมเสร็จ**

พิมพ์ตัวเล็กหรือมีขีดคั่นก็ค้นเจอ (`trk-999` = `TRK999`)

### ทำไมถึงไม่เปิดให้ดูทุกใบ
ใบแจ้งมีชื่อ เบอร์โทร และรูปภายในอาคาร ถ้าเปิดสาธารณะทั้งหมดจะเป็นการรั่วข้อมูลส่วนบุคคล
และทำให้คนนอกรู้ว่าห้องไหนอุปกรณ์เสีย — เสี่ยงด้านความปลอดภัยกายภาพ

ระบบจึงออกแบบให้:
- ต้องรู้รหัสเท่านั้นจึงเห็นใบนั้น (สุ่มจาก 32 ตัวอักษร 6 หลัก ≈ 1,000 ล้านชุด เดาไม่ได้)
- ข้อมูลที่คืนมามีแค่ **สถานะ อาคาร ห้อง ประเภทงาน เวลา** — **ไม่มีชื่อ ไม่มีเบอร์ ไม่มีรูป**
- ใช้ SECURITY DEFINER function จำกัดคอลัมน์ที่ระดับฐานข้อมูล ไม่ใช่แค่ซ่อนบนหน้าเว็บ

### สถิติหน้าแรก
แสดง 3 ตัวเลขแบบไม่ระบุตัวตน: ซ่อมเสร็จใน 30 วัน · ชั่วโมงเฉลี่ยต่องาน · กำลังดำเนินการ
(อัปเดตอัตโนมัติทุก 5 นาที)

### เตือนแจ้งซ้ำ
พอผู้แจ้งเลือกห้อง ระบบจะเช็คให้ว่าห้องนั้นมีเรื่องค้างอยู่กี่รายการ
ถ้ามีจะขึ้นข้อความเตือน — ลดใบซ้ำ ลดภาระเจ้าหน้าที่

## 9. หมายเหตุด้านเทคนิคของหน้าตา (UX/UI)

ระบบ **ไม่ใช้ 3D / WebGL** โดยตั้งใจ เพราะผู้ใช้หลักเปิดจากมือถือผ่านเน็ตมือถือ
และคนที่เข้ามาแจ้งซ่อมมักกำลังรีบ — ความเร็วสำคัญกว่าลูกเล่น

ใช้เทคนิค CSS สมัยใหม่แทน ซึ่งให้ผลลัพธ์สวยแต่ **เพิ่มขนาดไฟล์ 0 KB**:

| เทคนิค | ใช้ทำอะไร |
|---|---|
| `backdrop-filter` + เงาไล่ระดับ | การ์ดกระจก ความลึกแบบ layering |
| `linear()` spring easing | ปุ่มยุบตอนกด ให้ความรู้สึกเหมือนแอปมือถือ |
| `animation-timeline: view()` | เนื้อหาลอยขึ้นตอนเลื่อนถึง (ไม่ใช้ JavaScript) |
| View Transitions API | เปลี่ยนหน้าลื่นไม่กระพริบ |
| Skeleton loading | ระหว่างรอผลค้นหา |

รองรับเครื่องเก่าด้วย `@supports` fallback และปิดอนิเมชันอัตโนมัติให้ผู้ที่ตั้งค่า
"ลดการเคลื่อนไหว" (`prefers-reduced-motion`) ไว้ในเครื่อง

ธีมสี: ฟ้า–ขาวโทนมหาวิทยาลัย ตัวหนังสือใช้น้ำเงินเข้มเกือบดำ (อ่านสบายตากว่าดำสนิท)
ฟอนต์ IBM Plex Sans Thai ปรับ line-height 1.7 ให้เหมาะกับวรรณยุกต์ไทย
