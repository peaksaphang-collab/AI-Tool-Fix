Input · Process · Output

อะไรเข้า อะไรเกิดขึ้น อะไรออก

Input

  • รูปถ่าย JPEG/PNG/WEBP
  • อาคาร + ห้อง (เลือกจากรายการ)
  • ประเภทงาน (ไม่บังคับ)
  • ชื่อ + เบอร์ (ไม่บังคับ)
  • เวลาที่ใช้กรอก (จับอัตโนมัติ)

Process

  • ตรวจชนิดไฟล์และขนาด
  • อัปโหลดเข้า bucket ปิด
  • AI จำแนก 5 หมวด + 4 ระดับความด่วน
  • ออกรหัสติดตาม (ชนกันได้ 1 ใน พันล้าน จึงลองใหม่อัตโนมัติ)
  • คำนวณกำหนด SLA ตามความด่วน

Output

  • 1 แถวใน reports
  • 1 แถวประวัติสถานะ (จาก trigger)
  • รหัสติดตามคืนให้ผู้แจ้ง
  • คำทาย AI 2 ชุด: แช่แข็ง + แก้ได้

Display

  • บอร์ด 2 ฝั่ง เรียงตามความด่วน
  • ป้ายนับถอยหลัง SLA
  • Kanban ลากได้ · Timeline · Heatmap · ปฏิทิน
  • สรุปวัน/เดือน/ปี + ส่งออก CSV

ข้อสังเกตเชิงออกแบบ: ผู้ใช้แตะจริงแค่ 3 จุด (รูป → อาคาร → ห้อง) ที่เหลือระบบเติมให้เอง — ตัวเลข "เวลาที่ใช้กรอก" ถูกเก็บทุกใบเพื่อพิสูจน์ข้อนี้ด้วยข้อมูลจริง ไม่ใช่คำกล่าวอ้าง

AI Logic

AI ตัดสินใจอย่างไร และบังคับให้ตอบเป็นโครงสร้างได้อย่างไร

AI Logic

สัญญาระหว่างโค้ดกับ AI (Tool Schema)

// โครงสร้างที่บังคับให้ AI ตอบกลับ
{
  equipmentType: "เครื่องปรับอากาศ",
  description:   "มีน้ำรั่วซึมที่หน้ากากแอร์",
  confidence:    0.92,        // 0–1
  serviceTypeId: 3,           // enum 1–5
  urgency:       "high"      // 4 ระดับ
}

ทุกฟิลด์เป็น required และสองฟิลด์ท้ายเป็น enum — AI จึงเลือกได้เฉพาะค่าที่ระบบรู้จัก ไม่มีทางคืนหมวดที่ไม่มีอยู่

การจำแนกหมวด (5 ประเภท)

สุขาภิบาล · ไฟฟ้า · เครื่องปรับอากาศ · อาคาร · ครุภัณฑ์สำนักงาน — คำอธิบายในสคีมาบอกตัวอย่างของแต่ละหมวดให้ AI เทียบ เช่น "ประปา ท่อ สุขภัณฑ์" คู่กับหมวด 1

เกณฑ์ความเร่งด่วน

critical อันตราย/กระทบวงกว้าง (ไฟลัดวงจร น้ำท่วม) · high ใช้งานไม่ได้เลย · medium ใช้ได้บางส่วน · low เสียหายเล็กน้อย/ความสวยงาม

ตรวจซ้ำในโค้ด

ชนิดข้อมูลต้องถูก · หมวดต้องอยู่ 1–5 · ความมั่นใจถูกบีบเข้า 0–1 · ความด่วนต้องอยู่ในลิสต์ ไม่ผ่านข้อใดข้อหนึ่ง = ทิ้งค่านั้นเป็น null

Measurement

วัดความแม่นยำของ AI ได้อย่างไร

Security Model

ใครทำอะไรได้ — บังคับที่ชั้นฐานข้อมูล ไม่ใช่แค่ซ่อนปุ่ม

ตาราง / ทรัพยากรคนทั่วไป (anon)เจ้าหน้าที่ (ล็อกอิน)
reportsเพิ่มได้เท่านั้น — และถูกบังคับให้ status='pending', ห้ามตั้งผู้รับผิดชอบ/คะแนนเองอ่าน · แก้สถานะ · มอบหมาย · แก้หมวดที่ AI ทายผิด
buildings / rooms / service_typesอ่านได้ (ต้องใช้ทำ dropdown)อ่าน + จัดการรายการ
staffเข้าไม่ถึงเลยอ่านรายชื่อเพื่อมอบหมายงาน
report_status_historyเข้าไม่ถึงเลยอ่าน (เขียนได้เฉพาะ trigger)
รูปถ่าย (Storage)อัปโหลดได้ · ดูของคนอื่นไม่ได้ดูผ่าน signed URL อายุ 1 ชม.
ติดตามสถานะดูได้เฉพาะใบที่ถือรหัส 6 หลัก — และคืนเฉพาะฟิลด์ปลอดภัย ไม่มีชื่อ/เบอร์/รูปเห็นทั้งหมดในแดชบอร์ด

ทำไมไม่พึ่ง UI

ทุกข้อในตารางนี้เป็น Row Level Security ในฐานข้อมูล ถ้ามีคนยิง API ตรงข้ามหน้าเว็บ กฎยังบังคับอยู่เหมือนเดิม — การซ่อนปุ่มไม่ใช่ความปลอดภัย

บทเรียนจากการทดสอบจริง

นโยบายรุ่นแรกเช็คสิทธิ์โดย query ตาราง staff ตรง ๆ ทำให้เกิด infinite recursion — อ่านข้อมูลไม่ได้เลยทั้งระบบ แก้ด้วยฟังก์ชัน is_staff() แบบ SECURITY DEFINER พบจากการยิงทดสอบของจริง ไม่ใช่จากการอ่านโค้ด

Service Level

SLA — งานไม่ด่วนเท่ากัน เส้นตายจึงไม่ควรเท่ากัน

Realtime

ทำไมทุกจอเปลี่ยนพร้อมกันได้

กลไก

  • ตาราง reports ถูกใส่ใน publication ของ Realtime
  • แดชบอร์ดสมัครฟังเหตุการณ์ INSERT และ UPDATE
  • มีใบใหม่ → การ์ดแทรกขึ้นหัวรายการ + toast เตือนทันที
  • สถานะเปลี่ยน → การ์ดใบนั้นอัปเดตในที่
  • ออกจากหน้า → ยกเลิกการสมัครฟัง (ไม่ค้างเป็น memory leak)

Optimistic update

กดปุ่มแล้ว UI เปลี่ยนทันทีก่อนเซิร์ฟเวอร์ตอบ — ช่างไม่ต้องรอ ถ้าเซิร์ฟเวอร์ปฏิเสธ สถานะจะถูกดึงกลับเป็นค่าเดิม และข้อความจาก Realtime เป็นตัวตัดสินสุดท้ายเสมอ

ผลที่ผู้ใช้รู้สึก

เจ้าหน้าที่ 5 คนเปิดพร้อมกัน คนหนึ่งกดปิดงาน อีก 4 จอเห็นทันทีโดยไม่ต้องรีเฟรช — แก้ปัญหางานซ้ำซ้อนที่ระบบเดิมต้องโทรถามกันเอง

ข้อจำกัดที่ควรรู้: Realtime เป็นการแจ้งเหตุการณ์ ไม่ใช่แหล่งความจริง — หน้าเว็บยังโหลดข้อมูลตั้งต้นจากฐานข้อมูลทุกครั้งที่เปิด ถ้าเน็ตหลุดกลางทางแล้วต่อกลับ การรีเฟรชจึงยังให้ภาพที่ถูกต้อง

Technology

เครื่องมือที่ใช้ และเหตุผลที่เลือก

Next.js 16 (App Router)

หน้าเว็บและ API อยู่โปรเจกต์เดียว — Server Actions ทำให้ฟอร์มส่งตรงถึงเซิร์ฟเวอร์ โดยไม่ต้องเขียน REST endpoint แยก และคีย์ทั้งหมดอยู่ฝั่งเซิร์ฟเวอร์โดยธรรมชาติ

Supabase (PostgreSQL)

ได้ฐานข้อมูล + ล็อกอิน + ที่เก็บไฟล์ + Realtime ในบริการเดียว และที่สำคัญคือได้ RLS ซึ่งบังคับสิทธิ์ที่ชั้นข้อมูลจริง

Vision LLM + Structured Output

ใช้ความสามารถบังคับรูปแบบคำตอบ (tool schema) แทนการแกะข้อความ — ลดความเปราะของ prompt และตรวจสอบค่าได้ทันที

Tailwind + shadcn/ui

คอมโพเนนต์มาตรฐานเดียวกันทั้งแอป รองรับคีย์บอร์ดและ screen reader ทำให้หน้าตาสม่ำเสมอโดยไม่ต้องเขียน CSS ซ้ำ

Vercel

push ขึ้น main แล้ว deploy อัตโนมัติ ใช้ได้ฟรีในระดับโครงงาน และรองรับ Server Actions ของ Next.js โดยตรง

IBM Plex Sans Thai

ฟอนต์ไทยที่อ่านตัวเลขและอักษรผสมได้ชัด พร้อม fallback ถึงฟอนต์ระบบของ Windows / macOS / Android จึงไม่มีอักษรกล่องบนเครื่องใดเครื่องหนึ่ง

Summary

สามการตัดสินใจที่ทำให้ระบบนี้ต่างจากงานทั่วไป

1 · ระบบต้องรับแจ้งได้เสมอ

AI เป็นตัวช่วย ไม่ใช่เงื่อนไข ถ้า AI ล่ม หมด quota หรือไม่มีคีย์ ใบแจ้งซ่อมยังเข้าระบบครบ — เพราะสิ่งที่ผู้ใช้ต้องการคือให้ช่างมาซ่อม ไม่ใช่ให้ AI ทำงาน

2 · เก็บข้อมูลที่ย้อนกลับไปเก็บไม่ได้

คำทายเดิมของ AI · เวลาที่ใช้กรอกฟอร์ม · คะแนนความพึงพอใจ ทั้งสามอย่างถ้าไม่เก็บตอนนั้นก็หายตลอดไป และเป็นตัวชี้วัดทั้งหมดของงานวิจัย

3 · สิทธิ์บังคับที่ฐานข้อมูล

คนทั่วไปแจ้งซ่อมได้แต่อ่านข้อมูลคนอื่นไม่ได้ — บังคับด้วย RLS ไม่ใช่ด้วยการซ่อนปุ่มบนหน้าเว็บ ทดสอบแล้วด้วยการยิง API ตรง

สิ่งที่ต่อยอดได้ต่อจากนี้

แจ้งเตือนกลับผู้แจ้งผ่าน LINE/อีเมล · QR ประจำห้องเพื่อลดเหลือขั้นตอนเดียว · รูปหลังซ่อมเป็นหลักฐาน · ทะเบียนครุภัณฑ์เพื่อตอบว่าอุปกรณ์ไหนควรเปลี่ยนแทนซ่อม · ความเห็นในใบงานเพื่อลดการโทร
